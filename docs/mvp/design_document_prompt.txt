============================================================
PROJECT CONTEXT
============================================================

Correlius is a nonprofit, noncommercial Star Wars fan-film project.

The website has two major surfaces:

1. PUBLIC SITE
   correlius.org

   The public site centers the films themselves and allows ordinary
   viewers to understand the project and watch released episodes
   without authentication.

2. PARTNER EVIDENCE ROOM
   partners.correlius.org

   This is a controlled professional area intended for approved:
   - podcasters
   - forum/community moderators
   - convention organizers
   - journalists
   - clinicians
   - collaborators
   - prospective donors

   It contains audience evidence, editorial/feature materials,
   donor information, media resources, and collaboration materials.

The architecture should remain deliberately lightweight.

This is an MVP operated primarily by one technically capable creator.
The website must support the filmmaking effort rather than become a
second full-time job.

============================================================
KNOWN ARCHITECTURAL CONSTRAINTS FROM THE MVP
============================================================

Preserve these unless the source requirements explicitly say otherwise:

- GitHub for source control.
- Cloudflare Pages / Cloudflare edge delivery for static web hosting.
- Cloudflare Stream for video.
- Cloudflare Access for partner authentication.
- Email one-time PIN authentication for approved partners.
- Fractured Atlas handles donations.
- No custom donation processing.
- No custom CMS.
- No application database for MVP.
- No ordinary viewer accounts.
- No public comments/forums.
- No paid memberships.
- No native mobile application.
- No live streaming.
- No raw survey datasets deployed to the website.
- No sensitive legal/insurance/participant material in the public repository.
- No unnecessary advertising trackers.
- Cloudflare-native analytics, security, CDN, and alerting should be preferred where they satisfy the requirement.
- GitHub-based deployment should remain simple and reversible.
- Public content and partner content must remain architecturally separated.
- Partner content must be deny-by-default.
- The design must support at least four Correlius Journal episodes without redesign.

Do not introduce AWS, Azure, Firebase, Supabase, Auth0, WordPress,
Contentful, a relational database, Kubernetes, Docker infrastructure,
microservices, or another major platform unless an explicit MVP
requirement makes it unavoidable.

If Cloudflare/GitHub functionality is sufficient, prefer it.

============================================================
ARCHITECTURAL PRINCIPLES
============================================================

Optimize the design in this order:

1. Requirements correctness
2. Security and privacy
3. Accessibility
4. Reliability
5. Low/no operating cost
6. Operational simplicity
7. Maintainability by one owner
8. Performance
9. Extensibility
10. Architectural elegance

Avoid overengineering.

Apply YAGNI aggressively.

Prefer static content and configuration over dynamic services.

Prefer configuration over custom code where Cloudflare or GitHub
already provides the required capability.

Do not design for hypothetical millions of users beyond ensuring the
static/edge architecture can naturally tolerate traffic growth.

Do not turn future possibilities into MVP components.

============================================================
IMPORTANT SECURITY MODEL
============================================================

Treat the partner evidence room as genuinely private content.

robots.txt and noindex are NOT security controls.

The design must ensure that unauthenticated users cannot retrieve
partner content or protected files even when they know the direct URL.

Analyze:

- Cloudflare Access enforcement
- approved-email allowlisting
- one-time PIN authentication
- session expiration
- revocation
- authentication logging
- rate limiting
- WAF/bot protections
- protected downloads
- direct URL access
- indexing prevention
- secrets management
- GitHub branch protection
- GitHub and Cloudflare 2FA
- least-privilege Cloudflare API tokens
- CSP
- HSTS
- X-Content-Type-Options
- frame restrictions
- Referrer-Policy
- DNSSEC
- registrar protections
- SPF/DKIM/DMARC where applicable
- security.txt
- dependency vulnerability management
- deployment supply-chain security

Explicitly identify trust boundaries.

Never place an allowlist, credential, API key, secret, participant
identifier, raw survey response, or sensitive donor/legal material in
client-side JavaScript or the public Git repository.

============================================================
VETTED PARTNER PORTAL
============================================================

US-08 is amended: Correlius does not accept partner applications
online. Brian vets and approves partners privately.

Design the public partner page and protected portal so that:

- the public page explains that access is by private approval only
- the public page links only to https://partners.correlius.org/
- no public application or registration form exists
- no prospective-partner submission endpoint, Turnstile flow,
  application database, KV marker, or notification email exists
- visiting or attempting to sign in does not request access
- only exact email addresses Brian approved privately can match the
  Cloudflare Access Allow policy
- Cloudflare Access remains deny by default for all portal resources

Do not introduce an online application path or automated approval.

Explicitly identify any requirement that cannot be satisfied cleanly
without some state/storage and propose the smallest acceptable state
mechanism.
